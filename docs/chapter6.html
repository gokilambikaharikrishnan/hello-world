Chapter 6 — BMS Architecture

Building the Brain:
BMS Architecture

A BMS is not a single chip or a few protection FETs — it is a layered system of hardware and firmware modules, each solving a specific physical problem. This chapter traces every architectural decision from battery physics to silicon: AFE ICs, MCU peripherals, CAN bus framing, NVM wear leveling, RTC timestamping, state machines, and SOX algorithms. By the end, you will be able to design a production-grade BMS from a blank schematic.

Section 6.1

BMS Requirement Traceability

Every component in a BMS exists because of a specific battery physics problem. There is no unnecessary hardware. Understanding this traceability is the foundation of good BMS design — it tells you why each module exists, what it must do, and what happens if it fails. This section maps the complete chain from battery weakness to silicon implementation.

The Fundamental Principle of BMS Architecture

A well-designed BMS has zero gratuitous complexity. Every IC, every firmware module, every communication message exists because removing it would allow a specific battery failure mode. When designing a new BMS, the correct starting point is the traceability matrix above — not the BOM, not the MCU spec sheet. Physics first, silicon second.

Section 6.2

Hardware Architecture — Full Picture

A production BMS comprises six hardware layers: cells, the Analog Front End (AFE), the microcontroller (MCU), communication interfaces, persistent storage, and physical protection (FETs, fuse, contactor). Each layer has a specific job and communicates with adjacent layers through well-defined interfaces. Failure to understand these boundaries is the most common source of BMS design bugs.

AFE Layer — Deep Dive

The Analog Front End IC is the most safety-critical component in the BMS. It sits between the high-voltage cell stack and the low-voltage MCU, performing differential cell voltage measurement, temperature reading, short-circuit detection, and balancing FET control — all simultaneously, all on every cell, all with galvanic isolation to protect the MCU.

Flying Capacitor — Why It's Necessary
In a 16S pack, cell 16 sits at ~52V above ground while cell 1 sits at ~3.3V. Connecting both directly to a single ADC is impossible — the common-mode voltage would saturate or destroy the input. The flying capacitor multiplexer solves this by charging a small capacitor (C_fly) across each cell differentially, then transferring that charge to the ADC input. The ADC only ever sees a differential voltage of ≤3.65V — never the full stack voltage. This is why AFE ICs are expensive: the flying capacitor architecture requires 16 high-voltage switches inside the IC.
Delta-Sigma ADC — How It Works
The Δ-Σ (delta-sigma) ADC does not flash-convert the voltage directly. Instead, it oversamples at a very high rate (1–4 MHz) using a 1-bit comparator, then applies a digital decimation filter to produce a 16-bit result. This architecture is immune to thermal noise because averaging 1000s of 1-bit samples produces a statistically precise result. The tradeoff: each conversion takes ~1ms per cell. For 16 cells, the AFE needs ~16ms per full cycle — which is why the firmware measurement loop runs at 10ms (AFE pipelines the conversions).
AFE Watchdog — The True Fail-Safe
The AFE watchdog is the most important safety feature that most engineers overlook. The MCU must write 0xA5 to the AFE's watchdog register every ≤2 seconds. If the MCU crashes (stack overflow, firmware bug, power glitch) and stops writing, the AFE watchdog timer expires and the AFE independently opens all protection FETs. The battery is now safe even with a dead MCU. UL 1973 Phase 5 tests this explicitly: the tester freezes the firmware and watches for the watchdog response. Without this, no UL 1973 certification.
SPI Daisy Chain for Multi-Pack
A single BMS may manage 2–4 AFE ICs (for very large packs). TI BQ76952 uses standard SPI, requiring one CS line per IC. ADI LTC6813 uses isoSPI — a differential, isolated version that chains multiple AFEs in a ring topology with a single twisted pair. Each AFE receives commands, acts on its cells, appends its data, and passes the packet downstream. The MCU talks only to the first AFE; the last AFE returns the combined data. This allows 18 cells per AFE × N AFEs = practically unlimited cell count from one MCU SPI port.

MCU Layer

The MCU is the brain of the BMS — it runs all firmware modules, manages state transitions, and coordinates between the AFE, storage, and communication subsystems. Selecting the wrong MCU is one of the most expensive engineering mistakes: insufficient RAM means SoC algorithms cannot run; insufficient Flash means the OCV lookup table doesn't fit; missing CAN peripheral means an external controller IC is needed.

Why Dedicated MCU for BMS
Some designs try to share an MCU between the BMS and inverter control. This is dangerous: if the inverter control loop takes a long CPU burst (e.g., MPPT recalculation), the BMS measurement loop is delayed — a 100ms measurement gap during a fault condition can allow cell damage. Production BMS systems always use a dedicated MCU. The cost of a second $2 MCU is far less than the liability of a missed protection event. Dedicated MCU also simplifies UL 1973 fault-injection testing since the entire firmware under test is the BMS.
Core Clock Speed Requirements
A 48–168 MHz Cortex-M0+ to M4 is sufficient for most BMS applications. The EKF SoC algorithm (Chapter 2) requires floating-point matrix operations; an FPU (Cortex-M4F or M7F) eliminates software floating-point overhead. Rule of thumb: measure CPU load at peak — measurement + protection + SoC + CAN TX should consume less than 60% CPU budget, leaving headroom for balancing, logging, and future features. Never design at 95% CPU utilisation — debugging interrupt latency issues at 3am is expensive.
RAM Requirements
Minimum for a 16S LFP BMS: 32KB RAM. Breakdown: cell voltage array (16×2B = 32B), temperature array (6×4B = 24B), EKF state matrix (4×4 float = 64B), OCV-SoC lookup table if in RAM (50×8B = 400B), circular log buffer (256×16B = 4KB), CAN TX/RX buffers (8×16B = 128B), RTOS task stacks (4KB typical per task × 4 tasks = 16KB). Recommended: 64KB+ RAM to avoid tight-margin designs that fail in cold (-40°C) when stack depth increases with slower execution.
Flash Requirements
Code size for a complete BMS firmware: 64–128KB typical. Breakdown: RTOS kernel (~12KB for FreeRTOS), BMS application code (~40KB), OCV lookup table (400B), NVM driver (~4KB), CAN stack (~8KB), calibration data in Flash (2KB). Always leave 25% Flash free for firmware updates (OTA or bench-programmed). NVM sectors require separate Flash pages to avoid code corruption during write. Minimum recommended: 256KB Flash.
Required Peripherals
Must-have: SPI (AFE communication), ADC (NTC temperature, shunt voltage, pack voltage), CAN or CAN-FD (host communication), UART (debug/service interface), timers (measurement loop, balancing timing, watchdog), hardware watchdog timer (WDT — must be separate from RTOS tick), I²C or SPI for EEPROM/Flash NVM, RTC (timestamping), backup domain power (for backup SRAM + RTC on power loss). Nice-to-have: DMA (SPI transfers without CPU intervention), hardware CRC (NVM integrity), IWDG (independent watchdog — clocked from LSI, separate from main clock).
Watchdog Timer Design
A BMS must have two watchdog layers: (1) AFE hardware watchdog — opened by AFE IC if MCU stops writing WDOG register; (2) MCU independent watchdog (IWDG) — resets the MCU if firmware hangs. The IWDG uses the LSI oscillator (32kHz), independent of the main system clock, so a PLL failure does not affect the watchdog. The watchdog must be fed by the measurement loop — not by a separate task. If the measurement loop hangs, the system resets. Configure timeout: 100ms for IWDG (allow measurement loop to slip one cycle), 2s for AFE watchdog (allow MCU reset and reinitialisation).

CAN Bus — Deep Dive

CAN (Controller Area Network) is the dominant communication protocol for BMS-to-inverter communication in stationary ESS. Developed by Bosch in 1986 for automotive, it offers differential signaling (noise immunity), hardware error detection (CRC + bit stuffing), and bus-level arbitration — no master/slave collisions. Understanding CAN framing is essential for BMS integration work.

CAN Error Handling and Bus-Off

Error Counters (TEC / REC)
Every CAN node maintains a Transmit Error Counter (TEC) and Receive Error Counter (REC). Each detected error increments the counter; successful frames decrement it. States: Error Active (TEC/REC <96) → Error Passive (TEC/REC 96–127) → Bus-Off (TEC ≥128). In Bus-Off, the node disconnects from the bus and waits for 128 × 11 recessive bits before re-joining. This prevents one faulty node from destroying the entire bus.
BMS Silent Timeout
UL 1973 requires the host (inverter) to detect BMS silence within 5 seconds. Implement this in the inverter firmware: if no CAN message from BMS ID 0x355 received in >5s, the inverter must cease charging/discharging and raise an alarm. The BMS also monitors this in reverse — if CAN TX fails continuously (bus-off state), it logs a communication fault and opens FETs after a configurable timeout (default: 30s to allow bus recovery).
Baud Rate: 250 vs 500 kbps
250 kbps is the industry standard for stationary ESS (PYLON, SMA, Victron, Growatt all use 250kbps). Maximum bus length at 250kbps: ~250m (5 ns/m propagation). 500 kbps halves this to ~100m. For home ESS where BMS and inverter are in the same cabinet, 500 kbps works fine. For UPS with remote monitoring over longer cable runs, stick to 250 kbps. Both ends must match exactly — a baud mismatch produces immediate bus errors.

NVM & Backup SRAM

When a BMS loses power, it must remember its state — SoC, SoH, cycle count, fault history, calibration. Without this, every power cycle causes SoC to revert to an OCV-based estimate (which is inaccurate on the LFP flat plateau) and cycle count resets to zero. Non-volatile storage and battery-backed SRAM solve this, but each has tradeoffs around write speed, endurance, and data integrity.

NVM Wear Leveling
EEPROM endurance: 100,000–1,000,000 write cycles. If SoC is written every 60s for 10 years: 10yr × 365d × 24h × 60 = 5,256,000 writes. This would destroy a single EEPROM address in ~5 years. Wear leveling rotates writes across a sector of N pages. With 16 pages and 1M endurance, the effective life extends to 16M writes — over 30 years. Implement by maintaining a write pointer that advances to the next page on each write, wrapping at N. A valid-byte header identifies the current page on startup.
CRC Protection of NVM Data
A power loss during an NVM write leaves a partially written page — the data may appear valid but contain bit errors. Every NVM record must include a CRC-16 or CRC-32 checksum over the data payload. On startup, the MCU reads each NVM record and validates the CRC. If the CRC fails, the record is marked invalid and the previous valid record is used. Never boot from corrupted NVM data — this has caused field failures where a BMS reported 0% SoC and refused to discharge from a fully charged pack.
EEPROM vs Internal Flash
External EEPROM (I²C AT24C256, 32KB): simple byte-level writes, 100K cycles per byte, no erase-before-write required. Best for SoC/SoH records. Internal Flash (STM32 dual-bank): must erase full page (2KB) before writing, 10K cycles per page, fast read. Best for large OCV tables and firmware. The professional solution uses both: EEPROM for high-write-frequency data (SoC checkpoints, fault log), internal Flash for low-write configuration (calibration, OCV tables, firmware parameters).
Backup SRAM Architecture
STM32 backup SRAM (BKP_SRAM) is a 4KB SRAM powered from VBAT when main VDD is absent. A CR2032 coin cell (220mAh) can power 4KB SRAM + RTC for 10+ years at 1–2μA standby. On power loss, the MCU writes the current SoC, SoF, and critical fault flags to BKP_SRAM. On startup, the MCU reads BKP_SRAM and validates integrity (magic number + checksum). If valid, SoC is restored immediately — no OCV wait. This gives sub-millisecond SoC recovery after power interruptions — critical for UPS applications where 10ms switchover is expected.

NVM Write Pattern with CRC and Wear Leveling

#define NVM_SECTOR_PAGES 16 #define NVM_PAGE_SIZE 64 /* bytes per page */ #define NVM_MAGIC 0xBDA5 typedef struct { uint16_t magic; /* 0xBDA5 = valid */ uint16_t soc_x100; /* SoC * 100 (0–10000) */ uint16_t soh_x100; /* SoH * 100 (0–10000) */ uint32_t cycle_count; /* full cycles */ uint32_t timestamp; /* Unix seconds from RTC */ uint16_t crc16; /* CRC-16 of above fields */ } NVM_Record_t; static uint8_t nvm_write_ptr = 0; /* current write page */ void NVM_SaveState(BMS_State_t *bms) { NVM_Record_t rec; rec.magic = NVM_MAGIC; rec.soc_x100 = (uint16_t)(bms->soc * 100.0f); rec.soh_x100 = (uint16_t)(bms->soh * 100.0f); rec.cycle_count = bms->cycle_count; rec.timestamp = RTC_GetUnixTimestamp(); rec.crc16 = CRC16_Compute((uint8_t*)&rec, offsetof(NVM_Record_t, crc16)); /* Write to current wear-level page */ EEPROM_Write(nvm_write_ptr * NVM_PAGE_SIZE, (uint8_t*)&rec, sizeof(rec)); /* Advance pointer (ring buffer) */ nvm_write_ptr = (nvm_write_ptr + 1) % NVM_SECTOR_PAGES; } bool NVM_LoadState(BMS_State_t *bms) { /* Scan all pages, find newest valid record */ uint32_t newest_ts = 0; int8_t best_page = -1; NVM_Record_t rec; for (uint8_t i = 0; i < NVM_SECTOR_PAGES; i++) { EEPROM_Read(i * NVM_PAGE_SIZE, (uint8_t*)&rec, sizeof(rec)); uint16_t expected = CRC16_Compute((uint8_t*)&rec, offsetof(NVM_Record_t, crc16)); if (rec.magic == NVM_MAGIC && rec.crc16 == expected && rec.timestamp > newest_ts) { newest_ts = rec.timestamp; best_page = i; } } if (best_page < 0) return false; /* No valid record */ EEPROM_Read(best_page * NVM_PAGE_SIZE, (uint8_t*)&rec, sizeof(rec)); bms->soc = rec.soc_x100 / 100.0f; bms->soh = rec.soh_x100 / 100.0f; bms->cycle_count = rec.cycle_count; nvm_write_ptr = (best_page + 1) % NVM_SECTOR_PAGES; return true; }

RTC & Timestamping

A Real-Time Clock (RTC) is not optional in a production BMS — it is the foundation of calendar aging calculations, fault event auditing, and SoH trending. Without accurate time, you cannot answer the most important service question: "When exactly did this fault happen, and what was the battery doing for the 30 minutes before?"

Why RTC in BMS?
Calendar aging: The Arrhenius aging model requires total time spent at high temperature. Without RTC, you can only count operational hours — not hours at elevated temperature (which matters much more). A pack left at 40°C for 6 months ages twice as fast as one at 25°C — the BMS must know calendar time to predict this.

Fault timestamps: "Cell 8 hit 3.67V" is useful. "Cell 8 hit 3.67V on 2025-03-15 at 14:32:07" is actionable for warranty and field diagnosis.
RTC Backup Power
The STM32 RTC runs in the backup power domain (VBAT pin), fed by a CR1225 coin cell (3V, 48mAh). At ~0.5μA RTC current draw, a single coin cell runs the RTC for 48000 / 0.5 = 96,000 hours = ~11 years. The backup domain also powers the 4KB backup SRAM, adding ~1μA — still 7+ years total. This means a BMS retains accurate time and last-known SoC even after the main battery is fully discharged and the power supply is disconnected.
Unix Timestamp Format
Store timestamps as uint32_t Unix seconds (seconds since 1970-01-01 00:00:00 UTC). This handles all time arithmetic as simple integer subtraction — no calendar math needed in the BMS. Overflow: uint32_t wraps in year 2106 — not a problem for current designs. For event logs, store timestamp + event type in 6 bytes: 4B timestamp + 1B event type + 1B event data. A 256-entry circular log uses 256 × 6 = 1536 bytes — fits comfortably in EEPROM.
Calendar Aging via RTC
The BMS logs temperature samples (every 60s) and accumulates time-at-temperature bins. At each SoH update (hourly), the Arrhenius factor is applied: k_age = A × exp(−Ea / R·T). The integral of k_age over calendar time gives the total calendar aging contribution. This is added to cycle aging (from cycle counting) to give total SoH degradation. Without RTC, only cycle aging is tracked — calendar aging (significant for storage) is completely invisible.
