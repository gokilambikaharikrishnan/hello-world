Q01

FIFO Intuition — What a Queue Is and When to Use It vs a Stack

Fundamentals

A queue is a container where the first item added is the first item removed — First In, First Out. Think of a supermarket checkout line: customers are served in the order they arrived. No cutting in front, no serving from the back. The item that has waited longest is always served next.

The critical choice — queue vs stack — determines your traversal order. A stack (LIFO) processes the most recently added item first, which drives depth-first search: you dive deep into one branch before exploring siblings. A queue (FIFO) processes the earliest-added item first, which drives breadth-first search: you fully explore all neighbours at distance 1 before moving to distance 2. Use a queue whenever "fairness" (order of arrival) or "shortest distance" matters.

In embedded systems, queues are fundamental infrastructure. UART receive buffers, CAN message queues, audio sample buffers, DMA ping-pong buffers, FreeRTOS task event queues — all are circular FIFO queues. Data arrives in order, it must be processed in order, and there must be no gaps or reordering. A stack would process the most recent data first and discard older data — exactly wrong for a serial communication buffer.

FIFO property visualised: enqueue(A): front→[A]←back enqueue(B): front→[A][B]←back enqueue(C): front→[A][B][C]←back dequeue()→A: front→[B][C]←back dequeue()→B: front→[C]←back Stack vs Queue — same pushes, different orders: push/enqueue: A, B, C Stack pop: C, B, A (LIFO — last in first out) Queue deq: A, B, C (FIFO — first in first out) Queue → BFS: nodes explored level by level, shortest path first Stack → DFS: nodes explored depth-first, path may not be shortest
Rule of thumb: if you need "nearest" or "shortest" → queue + BFS. If you need "deepest" or "all paths" → stack + DFS.
/* Minimal queue using a fixed array — template for all queue cards */
#define MAXN 100001
int q[MAXN];
int head = 0, tail = 0;   /* head = front (dequeue here), tail = back (enqueue here) */

void enqueue(int x)  { q[tail++] = x; }
int  dequeue(void)   { return q[head++]; }
int  peek(void)      { return q[head]; }
int  empty(void)     { return head == tail; }
int  size(void)      { return tail - head; }

Gotcha

The simple array queue above wastes space — head never goes back, so the front of the array becomes dead space after dequeues. For a fixed-size queue that reuses space, use a circular queue (Q02/Q03). For BFS where you never go back, the simple array queue is fine and fast.

    Circular Queue — Array-Based, Head/Tail with Mod Wrap

    Fundamentals

    A circular queue (ring buffer) fixes the space-waste problem of a plain array queue: when tail reaches the end of the array, it wraps back to index 0. The array is treated as a ring — the slot after the last is the first. This allows a fixed-size buffer to be reused indefinitely without shifting or copying.

    Ring buffers are the standard data structure for embedded communication buffers. The UART RX ISR enqueues bytes at tail (with no blocking — it just stores and returns). The main loop dequeues from head. Producer and consumer operate independently, separated by the ring. This is lock-free when there is one producer and one consumer (the single-producer single-consumer ring buffer, SPSC), because head and tail are written by different contexts.

    #define CAP 1024   /* must be power of 2 for fast modulo: & (CAP-1) */

typedef struct {
    int buf[CAP];
    int head, tail, size;
} CircQ;

void cq_init(CircQ *q)         { q->head = q->tail = q->size = 0; }
int  cq_empty(CircQ *q)        { return q->size == 0; }
int  cq_full(CircQ *q)         { return q->size == CAP; }

void cq_enqueue(CircQ *q, int x) {
    q->buf[q->tail] = x;
    q->tail = (q->tail + 1) % CAP;  /* wrap tail */
    q->size++;
}

int cq_dequeue(CircQ *q) {
    int val = q->buf[q->head];
    q->head = (q->head + 1) % CAP;  /* wrap head */
    q->size--;
    return val;
}

int cq_peek(CircQ *q) { return q->buf[q->head]; }

    When capacity is a power of 2, replace % CAP with & (CAP-1) — bitwise AND is faster than modulo on embedded CPUs without hardware division. E.g. (tail + 1) & (CAP - 1). This is standard practice in embedded ring buffers where every cycle counts.

    Circular Queue — Full vs Empty Distinction (The Off-by-One Trap)

    Fundamentals

    When head == tail in a circular queue, is the queue empty or full? Both states look identical if you only track head and tail. This is the fundamental ambiguity of circular queues. There are three standard resolutions: (1) track a separate size counter, (2) waste one slot so full is defined as (tail+1)%CAP == head, or (3) use a boolean flag.

    Embedded UART ring buffer implementations almost universally use the size counter or the waste-one-slot approach. Getting this wrong is a silent, devastating bug: you either drop bytes on a "full" buffer that isn't actually full, or corrupt data by writing into a "not full" buffer that is.

    CAP=4 ring: indices [0,1,2,3] METHOD 1: separate size counter (used in Q02) empty: size == 0 full: size == CAP Cost: one extra integer METHOD 2: waste one slot (effective capacity = CAP-1) empty: head == tail full: (tail + 1) % CAP == head enqueue fills slot at tail then advances; never uses the slot just before head Cost: one wasted slot, but NO extra variable Example CAP=5, effective cap=4: [A,B,C,D,_] head=0, tail=4 → full: (4+1)%5=0==head ✓ [A,B,C,_,_] head=0, tail=3 → NOT full: (3+1)%5=4 ≠ 0 METHOD 3: use a boolean 'full' flag empty: head==tail && !full full: full flag == true Cost: one extra bool
    Method 2 (waste one slot) is most common in embedded code: no extra state, just one less usable slot. Method 1 (size counter) is clearest and safest for general use.
    /* Method 2: waste one slot — classic embedded idiom */
#define CAP 5   /* effective capacity = 4 */

typedef struct { int buf[CAP]; int head, tail; } RingBuf;

void rb_init(RingBuf *r)  { r->head = r->tail = 0; }
int  rb_empty(RingBuf *r) { return r->head == r->tail; }
int  rb_full(RingBuf *r)  { return (r->tail + 1) % CAP == r->head; }

int rb_enqueue(RingBuf *r, int x) {
    if (rb_full(r)) return -1;           /* drop: no space */
    r->buf[r->tail] = x;
    r->tail = (r->tail + 1) % CAP;
    return 0;
}

int rb_dequeue(RingBuf *r) {
    if (rb_empty(r)) return -1;
    int val = r->buf[r->head];
    r->head = (r->head + 1) % CAP;
    return val;
}
    CAP=5 (max 4 items). enqueue(1,2,3,4): after 4th, tail=4, (4+1)%5=0=head → full=true. 5th enqueue returns -1 (dropped) ✓. dequeue→1: head=1. now rb_full: (4+1)%5=0≠1 → not full. enqueue(5): buf[4]=5, tail=0. dequeue→2,3,4,5. head=tail=0 → empty ✓.
    Gotcha

    If you forget to handle the full case and overwrite, in an SPSC UART buffer the write pointer runs into the read pointer and corrupts the oldest unread byte. The receive handler silently drops or corrupts a character — this shows up as garbled serial output that disappears when you slow down the baud rate. Always guard enqueue with a full check.

    Deque — Insert and Delete from Both Ends

    Fundamentals

    A deque (double-ended queue) supports enqueue and dequeue from both the front and the back. It generalises both a stack (add/remove from same end) and a queue (add to one end, remove from the other). A circular array deque maintains two pointers — front and back — and allows O(1) operations on either end.

    In C++, std::deque is the standard. In C, you implement it with a circular array or a doubly linked list. The circular array version has better cache performance; the doubly linked list version has no fixed capacity.

    The deque is the backbone of the monotonic deque pattern (Q11–Q14) where you need to add to one end and remove from either end depending on conditions.

    #define DCAP 100001

typedef struct {
    int buf[DCAP];
    int front, back, size;
} Deque;

void dq_init(Deque *d)          { d->front = d->back = d->size = 0; }
int  dq_empty(Deque *d)         { return d->size == 0; }

void dq_push_back(Deque *d, int x) {
    d->buf[d->back] = x;
    d->back = (d->back + 1) % DCAP;
    d->size++;
}

void dq_push_front(Deque *d, int x) {
    d->front = (d->front - 1 + DCAP) % DCAP;  /* move front back */
    d->buf[d->front] = x;
    d->size++;
}

int dq_pop_front(Deque *d) {
    int val = d->buf[d->front];
    d->front = (d->front + 1) % DCAP;
    d->size--;
    return val;
}

int dq_pop_back(Deque *d) {
    d->back = (d->back - 1 + DCAP) % DCAP;
    int val = d->buf[d->back];
    d->size--;
    return val;
}

int dq_front(Deque *d) { return d->buf[d->front]; }
int dq_back(Deque *d)  { return d->buf[(d->back - 1 + DCAP) % DCAP]; }
    push_back(1,2,3): front=0,back=3. back()=buf[2]=3. front()=buf[0]=1. push_front(0): front=DCAP-1, buf[DCAP-1]=0, size=4. pop_front()→0: front=0. pop_back()→3: back=2. Result: deque=[1,2], front=0,back=2 ✓
    Gotcha

    When moving front backwards (push_front), use (front - 1 + DCAP) % DCAP — not just (front - 1) % DCAP. In C, -1 % N can be negative (implementation-defined before C99, defined as truncation toward zero in C99+). Adding DCAP before the mod guarantees a non-negative result.

    Queue Using Two Stacks — How and Why It Works

    Fundamentals

    Implement a FIFO queue using only two LIFO stacks. The trick: one stack (inbox) receives all enqueues. When a dequeue is needed and the outbox is empty, pour everything from inbox into outbox — this reversal converts LIFO order into FIFO order. Subsequent dequeues are served directly from outbox until it empties again.

    The amortised analysis: every element is moved at most once from inbox to outbox. So n enqueues and n dequeues total at most 2n push/pop operations — amortised O(1) each. This pattern appears in lock-free concurrent queues where inbox and outbox can be independently locked, reducing contention.

    This card revisits the concept from stacks.html (ST30) but now from the queue perspective — emphasising why the double-reversal produces FIFO order.

    typedef struct {
    int inbox[50001];  int in_top;
    int outbox[50001]; int out_top;
} TwoStackQ;

void tsq_enqueue(TwoStackQ *q, int x) {
    q->inbox[q->in_top++] = x;
}

int tsq_dequeue(TwoStackQ *q) {
    if (q->out_top == 0) {
        /* pour inbox into outbox — reverses order */
        while (q->in_top > 0)
            q->outbox[q->out_top++] = q->inbox[--q->in_top];
    }
    return q->outbox[--q->out_top];
}

int tsq_peek(TwoStackQ *q) {
    if (q->out_top == 0)
        while (q->in_top > 0)
            q->outbox[q->out_top++] = q->inbox[--q->in_top];
    return q->outbox[q->out_top - 1];
}

int tsq_empty(TwoStackQ *q) {
    return q->in_top == 0 && q->out_top == 0;
}

    Gotcha

    Pour from inbox to outbox ONLY when outbox is empty. If you pour every dequeue, you mix items from both stacks. The lazy-transfer rule — pour only when empty — is what guarantees FIFO order is maintained across multiple enqueue/dequeue interleaving.

    BFS explores a graph one "ring" at a time. Every node at distance d is fully processed before any node at distance d+1 is touched. The queue is the engine: enqueue a node, it will be processed later in arrival order.

    The key discipline: mark a node visited when you enqueue it, not when you dequeue it. Otherwise the same node enters the queue multiple times and you get exponential blow-up.

    Reach for BFS when Shortest path in an unweighted graph Each BFS layer = one more edge; first time you reach the target = minimum edges Level-order traversal of a tree Layer = tree depth; queue naturally groups siblings together Connected-component discovery Flood-fill from any unvisited node until the queue drains

    Graph: 0→1, 0→2, 1→3, 2→3, 3→4. Start at 0.

    Queue state at every step (visited marked *):
    Enqueue 0* queue: [0] Dequeue 0 → enqueue 1*, 2* queue: [1, 2] Dequeue 1 → enqueue 3* queue: [2, 3] Dequeue 2 → 3 already visited queue: [3] Dequeue 3 → enqueue 4* queue: [4] Dequeue 4 → no unvisited nbrs queue: [] BFS order: 0 1 2 3 4 Distances: 0→0, 1→1, 2→1, 3→2, 4→3
    Mark visited AT ENQUEUE TIME, not dequeue time. 
    #define MAXN 128
void bfs(int adj[][MAXN], int n_nbrs[], int n, int src) {
    int visited[MAXN] = {0};
    int dist[MAXN];
    int q[MAXN], head = 0, tail = 0;

    visited[src] = 1;
    dist[src] = 0;
    q[tail++] = src;

    while (head != tail) {
        int u = q[head++];
        for (int i = 0; i < n_nbrs[u]; i++) {
            int v = adj[u][i];
            if (!visited[v]) {
                visited[v] = 1;
                dist[v] = dist[u] + 1;
                q[tail++] = v;   /* mark BEFORE enqueue */
            }
        }
    }
}
    src=0, n=5 Step 1: dequeue 0, enqueue 1(d=1) 2(d=1) q=[1,2] Step 2: dequeue 1, enqueue 3(d=2) q=[2,3] Step 3: dequeue 2, 3 visited q=[3] Step 4: dequeue 3, enqueue 4(d=3) q=[4] Step 5: dequeue 4, done q=[] dist[] = {0,1,1,2,3}
    Gotcha — mark at enqueue, not dequeue

    If you set visited[v]=1 only when you dequeue v, then v can be enqueued multiple times before it's ever dequeued. For a complete bipartite graph that's O(E) extra entries — O(n²) wasted work.

    Q09 0-1 BFS with Deque BFS / Level-Order

    Standard BFS assumes all edges have equal cost. If edges cost either 0 or 1, you can still get O(V+E) shortest paths using a deque instead of a plain queue: cost-0 edges push to the front, cost-1 edges push to the back. This keeps the deque ordered by distance without a heap.

    Think of it as a lazy Dijkstra for the binary-weight special case.

    Reach for 0-1 BFS when Grid where some moves are free and others cost 1 Free moves (cost 0) go to deque front; paid moves go to back Minimum cost path where cost ∈ {0,1} Deque maintains non-decreasing dist order without sorting Shortest path with optional "teleport" edges Teleport = cost 0 (push front), walk = cost 1 (push back)
    Why push cost-0 to front? Distance doesn't increase — process it at same level.
    dist[] = INF initially, dist[src]=0 deque: [src] Dequeue front u: for each neighbour v with edge cost w: if dist[u]+w < dist[v]: dist[v] = dist[u]+w if w==0: push_front(v) ← same distance level if w==1: push_back(v) ← next distance level Deque always has at most 2 distinct dist values at any time. Front = current level, back = next level.
