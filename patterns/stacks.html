ST01

LIFO Intuition — What a Stack Is and When to Reach for It

Fundamentals

A stack is a container where the last item added is the first item removed — Last In, First Out. Think of a stack of plates: you always add and remove from the top. You cannot reach the bottom plate without removing every plate above it.

Stacks appear whenever you need to undo or backtrack in the reverse order of arrival. The C function call stack is the canonical example: when foo() calls bar() which calls baz(), the return order is baz → bar → foo — perfectly reversed. Each frame is pushed on entry and popped on return.

The two signal patterns that scream "use a stack": (1) you process something, and later encounter its matching counterpart — parentheses, tags, open/close brackets; (2) you need the most recently seen element that satisfies some condition — monotonic stack problems. Any time you say "I need to remember what I saw, and process it in reverse," a stack is the answer.

In embedded C, stacks are everywhere: the hardware call stack (SP register on ARM Cortex-M), ISR nesting (interrupts push processor state to the call stack), undo buffers in state machines, and explicitly managed stacks for DFS traversal without recursion.

Function call stack — return address and locals on hardware stack
Calls nest LIFO; CPU SP is a hardware stack pointer
ISR nesting on Cortex-M — exception frame pushed automatically
Hardware pushes R0–R3, LR, PC, xPSR on exception entry
Bracket / tag matching in a parser
Open tags pushed; closed tags must match the top
Undo/redo in a text editor or state machine
Reverse the action history LIFO
DFS traversal without recursion
Explicit stack replaces the implicit call stack
Expression evaluation — operands pushed, popped when operator seen
Operators consume the most recent operands
Core operations — only three matter:
push(x) — add x to the top pop() — remove and return the top element peek() — read the top without removing it LIFO property visualised: push(1): [1] push(2): [1, 2] push(3): [1, 2, 3] pop() → 3 stack: [1, 2] pop() → 2 stack: [1] pop() → 1 stack: [] Rule: if you push A then B then C, you will always see C before B before A.
When to reach for a stack: "I need to process something now, but I might need to revisit it when its counterpart arrives later — and that revisit happens in reverse order of arrival."
/* Minimal array stack — the template used by every stack card in this file */
#define MAXN 100000
int stk[MAXN];
int top = 0;                     /* top points ONE PAST the last element */

void push(int x)   { stk[top++] = x; }
int  pop(void)     { return stk[--top]; }
int  peek(void)    { return stk[top - 1]; }
int  empty(void)   { return top == 0; }
int  size(void)    { return top; }
push(5) → stk=[5], top=1 push(3) → stk=[5,3], top=2 push(8) → stk=[5,3,8], top=3 peek() → 8 (top-1=2, stk[2]=8) pop() → 8 stk=[5,3], top=2 pop() → 3 stk=[5], top=1 empty() → 0 (top=1, not 0)
Gotcha

top is the index of the next free slot, not the last filled slot. So peek = stk[top-1] and pop = stk[--top]. If you define top as the last filled index, every formula shifts by one — pick one convention and stick to it throughout your code.

    Stack Implementation — Array-Based with Top Pointer

    Fundamentals

    The simplest, fastest stack implementation: a fixed-size array plus a single integer top that tracks how many elements are in use. All operations are O(1) with no allocation, no pointer chasing, and excellent cache locality — every element is contiguous in memory.

    This is exactly how the hardware call stack works on ARM Cortex-M: the stack pointer (SP / R13) decrements on push and increments on pop. The hardware stack grows downward in memory; a software array stack typically grows upward (index 0 = bottom). The mental model is the same.

    In competitive programming and embedded firmware, the array-based stack is always the first choice. The only limitation is a fixed capacity — which is fine when the problem bounds are known.

    Any algorithm problem where the input size is bounded
    No malloc, no free, no fragmentation — just an array
    Embedded firmware stack for DFS or expression evaluation
    Heap may not exist; static allocation is safe
    ISR-safe stack (no dynamic allocation in interrupt context)
    malloc is not reentrant; static array avoids the problem
    Performance-critical inner loop needing O(1) guaranteed
    Array push/pop is a single store + increment
    Memory layout — top grows upward from index 0:
    index: 0 1 2 3 4 ... [5] [3] [8] [ ] [ ] ^ ^ bottom top=3 (next free slot) push(7): stk[3]=7, top=4 [5] [3] [8] [7] [ ] top=4 pop(): val=stk[3]=7, top=3 (just decrement — no erasure needed) [5] [3] [8] [7*] [ ] top=3 (* still in memory but logically gone) peek(): return stk[top-1] = stk[2] = 8 (no move)
    The "popped" value physically stays in the array — it's logically gone because top no longer covers it. The next push overwrites it.
    #define STACK_MAX 100000

typedef struct {
    int  data[STACK_MAX];
    int  top;              /* index of next free slot; 0 = empty */
} Stack;

void stk_init(Stack *s)         { s->top = 0; }
int  stk_empty(const Stack *s)  { return s->top == 0; }
int  stk_full(const Stack *s)   { return s->top == STACK_MAX; }
int  stk_size(const Stack *s)   { return s->top; }

void stk_push(Stack *s, int x) {
    s->data[s->top++] = x;   /* store then increment */
}

int stk_pop(Stack *s) {
    return s->data[--s->top]; /* decrement then read */
}

int stk_peek(const Stack *s) {
    return s->data[s->top - 1];
}
    stk_init: top=0 push(10): data[0]=10, top=1 push(20): data[1]=20, top=2 push(30): data[2]=30, top=3 peek(): data[2]=30 (top unchanged) pop(): --top=2, return data[2]=30 pop(): --top=1, return data[1]=20 empty(): top=1 → 0 (false)
    Gotcha

    push uses post-increment (top++): store first at top, then increment. pop uses pre-decrement (--top): decrement first, then read. Swap them and you read/write one slot off — an off-by-one that looks correct until the stack wraps. Always: push stores at current top then moves top up; pop moves top down then reads.

    Array stack: push = store at top then top++; pop = --top then read
  • top==0 → empty; top==STACK_MAX → full
  • peek = data[top-1] without moving top
  • All operations O(1), zero allocation, cache-friendly

    Stack Implementation — Linked List Based

    Fundamentals

    A linked list stack grows dynamically — no fixed capacity. The head of the list is the top of the stack: push prepends a new node to the front, pop removes the front node. Both are O(1).

    The trade-off: each push calls malloc and each pop calls free, which is expensive and non-deterministic in time. In an embedded system without a heap — or in a hard-real-time context where malloc latency is unacceptable — this is the wrong choice. In a general-purpose application where capacity is unknown and memory is available, it is fine.

    General-purpose stack when maximum depth is unknown at compile time
    Grows on demand — no capacity planning needed
    LRU cache node pool (nodes recycled from a free list)
    Free list is a linked-list stack of available nodes
    Teaching linked list pointer manipulation via stack
    Push/pop show prepend/delete-head patterns
    Stack top = linked list head. Push = prepend. Pop = remove head.
    Empty: top=NULL push(1): [1|next=NULL] top→[1] push(2): [2|next→[1]] top→[2]→[1] push(3): [3|next→[2]] top→[3]→[2]→[1] pop(): val = top->val = 3 old = top (save to free) top = top->next → top→[2]→[1] free(old) return 3
    typedef struct SNode { int val; struct SNode *next; } SNode;

typedef struct { SNode *top; int size; } LStack;

void ls_init(LStack *s)  { s->top = NULL; s->size = 0; }
int  ls_empty(LStack *s) { return s->top == NULL; }

void ls_push(LStack *s, int x) {
    SNode *n = malloc(sizeof(SNode));
    n->val  = x;
    n->next = s->top;  /* new node points at old top */
    s->top  = n;       /* top is now the new node */
    s->size++;
}

int ls_pop(LStack *s) {
    SNode *old = s->top;
    int val = old->val;
    s->top = old->next; /* top moves down one */
    free(old);
    s->size--;
    return val;
}

int ls_peek(LStack *s) { return s->top->val; }
    push(5): top→[5→NULL], size=1 push(9): top→[9→[5→NULL]], size=2 peek(): top->val=9 pop(): val=9, top→[5→NULL], free node9, size=1 pop(): val=5, top=NULL, size=0 empty(): top==NULL → 1 (true)
    Gotcha

    Save top to a temp pointer before advancing top = top->next, then free the saved pointer. If you free first, top->next is a use-after-free. Always: save the node to be freed, move the pointer, then free.

    Confidence Check

    Linked list stack: push = prepend to head; pop = remove head; top = head
  • Unbounded capacity — grows with malloc on every push
  • No random access — only top is visible
  • Prefer array stack in embedded / performance-critical code

    Stack Overflow and Underflow — Guards and Detection

    Fundamentals

    Stack overflow happens when you push onto a full stack. Stack underflow happens when you pop from an empty stack. Both are silent bugs if unchecked — overflow corrupts adjacent memory, underflow reads garbage data or crashes with an array-index fault.

    On ARM Cortex-M, hardware call-stack overflow is one of the leading causes of hard faults in embedded firmware. The stack grows downward into the heap; when it collides, you get data corruption that manifests far from the actual overflow. FreeRTOS and most RTOSes paint the stack with a known canary pattern and check it periodically.

    For software stacks in algorithms, the guard is simple: check before push (is top < STACK_MAX?) and before pop (is top > 0?). In competitive programming these checks are usually omitted since input bounds guarantee the depth; in production code they are mandatory.

    Embedded firmware — call stack overflow causes HardFault on Cortex-M
    Stack grows into heap; canary detection or MPU guard region
    Recursive DFS hitting stack depth limit
    Deep trees overflow the call stack — switch to iterative
    Bracket matching on malformed input (all opens, no closes)
    Stack grows to size of input — must cap or handle gracefully
    Calculator with deeply nested parentheses
    100 levels of nesting = 100 stack frames; check capacity
    Overflow: push when full. Underflow: pop when empty.
    OVERFLOW — push on full stack (top == STACK_MAX): stk[STACK_MAX] = x; // writes beyond array → UB / memory corruption top becomes STACK_MAX+1 → next pop reads stk[STACK_MAX] = garbage UNDERFLOW — pop on empty stack (top == 0): --top → top = -1 return stk[-1]; // reads before array → UB Canary pattern (embedded): Fill stack array with 0xDEADBEEF at init. Periodically check if canary near the top is still intact. If overwritten → overflow detected before crash.
    Guard pattern: check before every push and pop. Fail loudly (assert, error return, or halt) — silent corruption is far worse than a clean error.
    #define STACK_MAX 100000
#define CANARY    0xDEADBEEFu

typedef struct {
    int  data[STACK_MAX];
    int  top;
} Stack;

/* Returns 0 on success, -1 on overflow */
int stk_push_safe(Stack *s, int x) {
    if (s->top >= STACK_MAX) return -1;  /* overflow guard */
    s->data[s->top++] = x;
    return 0;
}

/* Returns INT_MIN on underflow */
int stk_pop_safe(Stack *s) {
    if (s->top == 0) return INT_MIN;     /* underflow guard */
    return s->data[--s->top];
}

/* Embedded canary check — call from a periodic timer ISR */
void stk_check_canary(Stack *s) {
    /* check top few slots for canary overwrite */
    for (int i = STACK_MAX - 4; i < STACK_MAX; i++)
        if ((unsigned)s->data[i] != CANARY)
            __asm volatile("bkpt 0");   /* halt debugger */
}
    Overflow: STACK_MAX=3, push 3 elements (top=3), push 4th: stk_push_safe: top(3) >= STACK_MAX(3) → return -1 ✓ Underflow: top=0, call pop: stk_pop_safe: top==0 → return INT_MIN ✓ Normal: top=1, pop: --top=0, return data[0] ✓
    Gotcha

    In competitive programming, the "safe" guards add a branch to every push/pop. People often skip them and rely on input bounds — that is fine for a contest. In any code that ships, skip the guards only if you can prove the bound is never exceeded. A defensive assert(top < STACK_MAX) that fires in testing is infinitely better than silent memory corruption in production.
