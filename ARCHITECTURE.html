Each mode is a different lens on your BMS firmware. Feed it source code, logs, or datasheets — it reads everything, understands the BMS domain, and produces structured documentation a new engineer can act on immediately.

Mode 01 Code Documentation
"How is this module built — and why was it built that way?"
The situation: A developer needs to modify NVM_WriteBlock() but has never touched the NVM module. They open the file. 900 lines of C. Six static variables. A state machine. Three layers of abstraction below. They have no idea where to start — or what they might break.

Without documentation, they guess. Or they interrupt a senior engineer for two hours. Either way, the team loses.
With DocGen — generated in 60 seconds
  • 10 structured sections — overview, hardware, config, functions
  • Every function explained: purpose, parameters, side effects
  • State machine diagram — every state and transition named
  • Data flow diagram — what comes in, what goes out, where
  • Design decisions — why this approach, what was traded off
  • Fresher warnings — what not to touch and why
Input: One module folder (.c + .h files)   |   Output: 10-section HTML design document with Mermaid diagrams
Mode 02 Subsystem Documentation
"How does this entire feature work — from hardware to application?"
The situation: You want to understand how State of Charge flows through the system. That means reading: MCAL ADC, CDD AFE, ESAL BATT_IF, SRVLayer NVM, ASW PowerComputation — five separate modules, five separate files, spread across the stack. No single document ties them together.

An engineer spends a day tracing the signal path manually, trying to hold all five layers in their head at once.
With DocGen — cross-layer intelligence
  • Reads all 5 layers simultaneously, understands relationships
  • End-to-end signal flow: raw ADC counts → calibrated SOC %
  • Cross-module dependency graph — who calls what and why
  • Sequence diagram: ADC measurement to NVM write, every step
  • Consolidated config table — all parameters across all layers
Input: Multiple modules across layers + optional spec docs   |   Output: Unified subsystem overview HTML
Mode 03 AI Code Review
"What is wrong, risky, or improvable in this module?"
The situation: A code review takes half a day. The reviewer checks style, logic, memory safety — but reviewers are human. They miss subtle issues: a buffer that's one byte too small, a state machine with an unhandled transition, a magic number with no explanation, a loop that stalls if a peripheral hangs.

These bugs reach production. In a battery system, production bugs can be dangerous.
With DocGen — tireless auditor mode
  • Memory safety: buffer bounds, pointer arithmetic, stack usage
  • State machine completeness: every transition, every edge case
  • Magic numbers flagged — every unexplained constant explained
  • ISR safety: variables shared between ISR and main, atomicity
  • Severity rating: Critical / Warning / Suggestion per finding
Input: Module .c + .h files   |   Output: Audit report — severity-rated findings, no hallucination
Mode 04 Event Log Analysis
"What actually happened during this test run — and why did it fault?"
The situation: A battery pack faults on the test bench. You have a 50,000-line CSV event log: timestamps, module IDs, event codes. Someone has to manually cross-reference each event code against the source code to understand what triggered what.

It takes a full day. The test cannot resume until the root cause is confirmed. The engineer doing it is the one you least want tied up for a day.
With DocGen — log meets code
  • Reads the log AND the source code together
  • Translates every event code into plain English
  • Reconstructs the exact sequence of events that led to the fault
  • Highlights anomalies: out-of-order events, missing heartbeats, timing gaps
  • Root cause section: most likely explanation with evidence from log
Input: Excel/CSV event log + module source code   |   Output: Timeline analysis, root cause report, anomaly flags
Mode 05 CAN Bus Log Analysis
"What was on the bus during this session — decoded into human signals?"
The situation: A 4-hour test session was recorded. The .trc file has 2 million CAN frames: raw hex IDs and data bytes. To make sense of it, an engineer opens VECTOR CANalyzer, loads the .dbc, filters signals, and manually looks for the window where something went wrong.

It's slow. It requires expensive tooling. And it still requires someone who knows what "normal" looks like.
With DocGen — your bus, explained
  • Reads .trc / .asc log + .dbc database together
  • Decodes every signal by name, value, unit, and timestamp
  • Detects anomalies: missing messages, out-of-range values, timing gaps
  • Summary report: what happened on the bus, when, what stood out
  • No VECTOR licence required — runs in VS Code
Input: .trc or .asc CAN log + .dbc file   |   Output: Decoded signal report, anomaly flags, HTML timeline
Mode 06 Full System Documentation
"How does the entire BMS product work — for an auditor or integration partner?"
The situation: An external auditor (ISO 26262, customer, IATF) needs a system description. A new integration partner needs to understand your CAN interface, your protection thresholds, your startup sequence. Your best engineer needs to write 50 pages of documentation. From scratch. For two weeks. While feature development stops.

This happens every time there's an audit. Every time there's a new customer.
With DocGen — audit-ready at a click
  • Reads the full codebase, schematics, and spec documents together
  • Produces a complete system overview: architecture, protection logic, comms
  • Hardware-to-software signal chain for every major feature
  • Protection thresholds table — every limit, every action
  • CAN interface section — every message, signal, and timing
Input: Full codebase + schematics + spec docs   |   Output: Complete BMS system description document
Mode 07 Datasheet Intelligence
"This IC has a 280-page datasheet. What do WE actually use — and how?"
The situation: Your AFE IC datasheet is 280 pages. The engineer implementing the driver reads every page, figures out which of the 200 registers are relevant to your design, and writes a driver from scratch. Six months later a different engineer needs to understand how cell balancing is triggered. They start from page 1 again.

Every new engineer repeats the same archaeology.
With DocGen — 280 pages → what matters
  • Reads the datasheet PDF and your driver code together
  • Identifies which registers, modes, and sequences your code actually uses
  • Explains each register in the context of your specific BMS design
  • Init sequence document: exact order, exact values, exact reason for each
  • Quick-reference card — the only part of the datasheet you need
Input: IC datasheet PDF + driver .c/.h files   |   Output: Simplified reference — only what your system uses
